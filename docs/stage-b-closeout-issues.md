# 阶段 B 收尾问题总结

> 更新时间：2026-08-25  
> 测试方式：以 Gazebo 无界面模式为正式方式  
> 当前结论：**阶段 B 尚未达到结束条件，不得冻结 `SingleFloorExplorer`，也不得进入双层验收。**

## 1. 当前状态

阶段 B 的主要模块已经实现：

- Scan/Map 门洞证据统一进入 `DoorFusion`；
- 候选生命周期由 `DoorCandidateManager` 单独管理；
- 使用 FAST-LIO、IMU 航向和连续度量任务坐标；
- 房内危险物扫描采用两个镜像观察位；
- 第二观察位以第一观察位局部点云为基准执行有界 ICP；
- 走廊最多一次反向补扫；
- 正式危险物 JSON 与调试 JSON 分离；
- 核心测试共 67 项通过，Python 编译和目标文件的空白检查通过。

但是，现有结果只能证明各组件和部分动态链路可工作，不能证明阶段 B 已稳定完成。
尚未得到同一代码版本、干净运行环境下连续 5 个 seed 的正式通过结果。

2026-08-26 的无界面真实 Gazebo 复测（seed `20260825`）在新的房内中心障碍保护代码上运行到
`sim_time=300.0 s` 后结束：完成 1 次进门、1 次出门，P1 锚点和 P2 三个 90°扇区均执行；
走廊推进因仿真运动停滞而超时，最终 `VISITED=1/4`、危险物 `0/1`，因此仍是不通过轮次。
该轮没有把房间几何中心当作必须到达的目标点。P2 沿门内法向前进时，若激光正前方 ±10°
的最近回波或前方安全分位距离小于 `room_motion_stop_distance=0.45 m`，立即停车并在已到达
的安全位置执行三扇区扫描；没有触发该条件时才前进至有界距离 `3.5 m`。这样房间中心有家具
或危险物时不会为了到达几何中心而继续顶撞，但当前 seed 没有触发中心障碍停车日志，仍需在
中心确有障碍物的 seed 上补充动态验收。

随后使用当前监视器口径在相同无界面真实 Gazebo 条件下复测 seed `20260823`，本轮达到单 seed
完整通过：`VISITED=4/4`、`floor_complete=true`、4 个确认门且 `pending=0`，两组左右门站
结构有效（最大配对误差 `0.1605 m`），`UNREACHABLE=0`，危险物 `1/1`、红方块误报 `0`，
最大位姿步长 `0.2145 m`，平均 RTF `0.7955`，仿真时间 `246.942 s`。四个房间均完成
进门、P1、P2 三扇区扫描、退出和局部回环。该轮证明“PENDING 不计入正式门数”的监视器
修正有效，但仍只是一个 seed，不能替代连续 5 个 seed 验收。

## 2. 已确认但不能作为最终通过的结果

### 2.1 监控器通过，但实际访问了假门

`logs/stage_b_final_metric_frame_v4/seed_20260823/result.json` 曾记录：

- `passed=true`；
- `VISITED=4`；
- `floor_complete=true`；
- `UNREACHABLE=0`；
- 危险物 1/1 正确；
- 仿真时间约 257.3 秒。

但事后按场景真值核对，第四个候选位于走廊末端附近，是地图墙端形成的假门；与此同时，
第一组左侧真实房门没有被访问。因此这轮必须判为失败，不能因为候选数和访问数都是 4
就认为完成了真实四房。

这暴露出当前监控器的盲点：

```text
4 个候选 + 4 次 VISITED
不等于
4 个真实房间
```

正式验收还需要增加不依赖绝对坐标的结构检查：四门应形成两个纵向门站，每个门站左右
各一扇。该检查用于拒绝“漏一个真实门，再由一个假门补足数量”的情况。

### 2.2 后续 turnaround_v1--v4 不能作为正式证据

中断外层 `docker exec` 后，容器内的 `run_stage_b_seed.sh` 没有同步退出。后续复查发现多个
runner、监控器和探索节点残留并发运行。它们共享 ROS 和 Gazebo 资源，造成：

- 节点同名注册互相替换；
- 旧监控器继续监听新一轮话题；
- CPU/GPU 竞争导致实时因子异常降低；
- 日志和结果目录可能对应不同代运行状态；
- 同一种子的非确定性被人为放大。

因此 `stage_b_final_turnaround_v1` 至 `v4` 只可用于定位失效模式，全部不得纳入正式通过
统计。后续 runner 必须保证收到 `INT/TERM` 时容器内进程树完整退出，并在每轮开始前检查
只有一个 runner、一个 Gazebo 和一组 ROS 节点。

## 3. 当前发现的算法问题

### 3.0 房间中心可能被障碍物占据

房间的几何中心不能作为强制导航目标。第二观察位只是沿门内法向的有界前进点，前进过程中
同时使用正前方窄扇区最近距离和原有前方安全分位距离做碰撞保护。低于安全阈值时保留当前
位置作为第二观察位，停止平移并继续旋转扫描；因此家具遮挡不会让扫描状态被静默丢弃。

状态：**代码和静态测试已完成；本轮真实 Gazebo 未遇到中心障碍，需后续专门构造/选择该场景验证。**

### 3.1 走廊末端假门

掉头后，累计地图可能把走廊末端墙边约 0.9 米的缺口识别为小门。原先为此增加的在线掉头
位置排除区已经删除，避免把候选生命周期和门真假判定分成两套规则。现在统一由短时局部
`DoorVerifier` 检查两侧门框支撑与中间可通行间隙；点云不足时返回 `INCONCLUSIVE`，不误删候选。

状态：**核心逻辑和单测已完成，尚未在干净动态轮次中验证。**

### 3.2 穿门成功过度依赖“走廊结构消失”

机器人进入真实房间后，激光仍可能通过门口看到走廊双墙。旧逻辑一直等待走廊结构失效，
最终两次穿门超时并将真实门标为 `UNREACHABLE`。

现增加相对门中心的度量进入条件：沿门内法向达到至少 0.65 米即可确认进入；原有前方碰撞
保护、最短穿越时间和 14 秒上限仍保留。

状态：**代码已修改，尚未在干净完整轮次中验证。**

### 3.3 出门成功过早

旧退出逻辑只要重新看到走廊结构并稳定 0.7 秒，就认为已经回到走廊。实际测试中机器人
仍在右侧房间内，也能透过门口看到走廊，因此提前结束 `EXIT_ROOM`。随后机器人在房间内
沿走廊方向前进，撞到房间边界后出现“走廊进度停滞”和错误反向扫描。

现改为相对同一门中心的度量退出条件：沿门外法向进入走廊侧至少 0.45 米并稳定 0.7 秒，
才能结束退出。该条件与进房条件对称，不读取 Gazebo 真值。

状态：**代码已修改，局部诊断证明方向正确，但尚未完成干净四房验证。**

### 3.4 大厅到窄走廊的边界被当作房门

某轮将大厅/走廊过渡边界的左右开口识别为宽 1.14 米和 1.43 米的两个房门。此前为此增加
的入口进度截止线已经删除，避免再维护一条与门真假判定重复的历史过滤分支。长走廊确认仍
只负责检测上下文门控，疑似门的局部真假交给 `DoorVerifier`。

状态：**代码已修改，修改后的动态轮次因进程并发污染而无有效结论。**

### 3.5 同一危险物被拆成两条轨迹

一次诊断中，同一真实红球形成两条相距约 0.824 米的轨迹。主轨迹有 52 帧支持且位置准确，
第二条只有 2 帧，属于视角切换和局部漂移下的瞬态拆分，不是红方块误报。

危险轨迹正式确认门槛已由 2 帧恢复为 3 帧。真实目标在房间扫描中通常有数十帧支持，
提高一帧不会影响正常确认，同时可以挡住本次 2 帧假轨迹。

状态：**代码已修改，仍需在 5 个 seed 中验证零漏检、零重复和红方块误报为 0。**

### 3.6 LIO 长走廊漂移与尺度压缩仍是基础风险

不同运行中曾出现：

- 长走廊纵向位移被明显压缩；
- 横向漂移使同一扇门从不同局部地图位置重复出现；
- 房内旋转后候选和危险物位置发生偏移；
- 扫描匹配短时停滞导致错误恢复。

为此已实现连续度量任务坐标、走廊中心线约束、房间动作期间的有界命令积分，以及同门局部
回环。局部 ICP 实测单次约 1.6--4.3 毫秒，修正量约 0.03--0.09 米的轮次质量较好；也有
一轮出现约 0.75 米但仍在 1 米上限内的修正，说明质量阈值和大修正后的任务行为仍需观察。

状态：**机制已具备，但多 seed 稳定性尚未证明。**

### 3.7 容器内无界面复测结果

使用现有 `simenv-noetic` 容器，以 Gazebo 无界面模式复测种子 `20260823`。本轮确认：

- ROS Noetic、Gazebo、FAST-LIO、行为节点和 `DoorVerifier` 订阅链路均可启动；
- 完成 2 次进门、2 次出门，2 次同门局部回环均接受，最大局部修正约 0.12 m；
- 平均实时因子约 0.89，定位状态保持 `GOOD`；
- 但只访问 2 个房间，`floor_complete=false`，危险物 1 个漏检，正式结果不通过；
- 本轮没有出现 `DoorVerifier` 明确拒绝日志，因此尚不能证明它已抑制走廊端点假门。

本轮超时清理还发现 Gazebo 的 `gzserver` 被 ROS launch 拆到独立进程组。runner 已改为递归
按本轮 PID 树清理，并手动清理了本轮残留的两个精确 Gazebo PID；当前容器内没有 Stage B
或 Gazebo 残留进程。

## 4. 测试与运行环境问题

### 4.0 动态验收资源隔离

`run_stage_b_seed.sh` 现采用独立 ROS master 端口，并在启动前拒绝同一容器内已有的
Gazebo、FAST-LIO、Stage B 节点或占用中的测试端口。进程检查使用 `pgrep` 获取目标进程，
避免把检查命令自身的 `gzserver` 参数误判为冲突。动态轮次可通过
`SIMNAV_CPU_LIST=12-23` 将本轮 Gazebo、ROS、FAST-LIO 和行为节点绑定到指定 CPU 集合；
脚本会把实际端口和 CPU 集合写入该轮 `resource_guard.log`。这避免了不同轮次共享 ROS/Gazebo
资源，但不能替代主机级 CPU/GPU 负载管理；若外部 Gazebo 在其他容器或主机命名空间运行，
正式动态验收仍应先停用它或为 SimEnv 分配独立 CPU/GPU 资源。

### 4.1 runner 的退出语义

`run_stage_b_seed.sh` 现已加入单实例 `flock`、独立进程组和按本轮 PID 的退出清理；
`auto.sh` 不再执行全局 ROS/Gazebo `pkill`，因此不会主动清理其它任务。2026-08-25 的
无界面动态轮次中断后，已确认本轮进程树归零。

### 4.2 当前机器有其他 GPU 任务

2026-08-24 复查时，后台存在与 SimEnv 无关的 ActiveINR Habitat 仿真/可视化任务，约占用
4.2 GiB GPU，另有 Rerun 和任务仪表盘。它们不共享 SimEnv 的 ROS/Gazebo 进程；本记录也
不会停止它们。正式阶段 B 的 RTF 结果仍应注明主机整体 CPU/GPU 负载背景，不能把资源竞争
导致的低 RTF 直接归因于算法。

SimEnv 容器当前没有 Gazebo、阶段 B runner 或探索算法在运行；只存在若干历史只读
`rostopic echo/hz` 探针，几乎不占计算资源。

### 3.8 DoorVerifier 融合修正后的状态

上一轮 100 秒定向动态复测暴露出：楼梯 defer 区虽然已发布，但在线 Scan 证据仍可绕过
`DoorVerifier` 直接被 `DoorFusion` 单独确认。现已修正为：

- Scan-only 证据必须得到 `VERIFIED` 的门框/通行间隙结果才可确认；
- `INCONCLUSIVE` 的 Scan 只能等待 Map 互证；
- `REJECTED` 证据不能创建 hypothesis；
- `MAP_STRONG` 仍按方案允许在 `GOOD` 定位下独立确认。

修正后核心测试为 63 项全部通过，隔离 ROS 端口 `11333` 的完整离线验收达到
`VISITED=4`、`floor_complete=true`、危险物 `1/1`。修正后的动态 smoke 轮次因主机负载
过高，约 184 秒主机时间只推进到 13 秒仿真时间，未形成有效动态结论，已主动停止并清理。
在 activeINR 继续运行的当前环境中，第二轮使用 `SIMNAV_CPU_LIST=12-23` 和端口 `11336`，
约 170 秒主机时间只推进到 11 秒仿真时间；确认 CPU 绑定有效，但共享 GPU 仍使该轮不具备
正式验收意义。该轮已向本轮 runner 根 PID 发送 TERM，并确认 Gazebo、FAST-LIO、行为节点和
监控器全部退出。

## 5. 重新验收前必须完成的事项

1. 在 activeINR 保持运行的当前环境中，继续使用独立 ROS 端口、CPU 集合和本轮 PID 清理机制做无界面动态 smoke，验证 `DoorVerifier`、对称进出门和端点假门抑制；该环境的低 RTF 只能作为资源竞争记录，不能冒充正式性能结果。
2. 确认正式危险物 JSON 只有当前楼层真危险物，重复、红方块误报和漏检均为 0。
3. 固定同一代码版本，连续运行至少 5 个 seed，不在中途按单 seed 修改参数。
4. 每轮记录 `resource_guard.log`，明确 ROS 端口和 `SIMNAV_CPU_LIST`；发现未知 Gazebo/Stage B 进程时拒绝启动。

## 6. 阶段 B 正式结束条件

每个 seed 都必须同时满足：

| 指标 | 要求 |
|---|---:|
| 第一层真实房间 | 4/4 |
| `floor_complete` | `true` |
| `UNREACHABLE` | 0 |
| 额外假门 | 0 |
| 单房进入尝试 | 不超过 2 |
| 退出尝试 | 不超过 2 |
| 反向回扫 | 不超过 1 |
| 定位节点崩溃 | 0 |
| 大于 1 米非物理位姿跳变 | 0 |
| 人工干预 | 0 |
| 红方块误报 | 0 |
| 正式结果 JSON | 可直接评分 |
| 单层耗时 | 优先小于 360 秒，理想小于 300 秒 |
| 连续 seed | 至少 5 个通过 |

在上述条件完成前，阶段 B 的准确状态是：**功能链已基本形成，收尾失败模式已定位并进入
修正，但动态稳定验收未完成。**
