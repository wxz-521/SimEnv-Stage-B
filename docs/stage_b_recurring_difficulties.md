# Stage B：反复出现的困难，以及它们暴露的方法缺陷

> 只记录**当前仍在反复出现**的问题（已解决的一次性故障不列入）。每条给出：现象、证据轮次、它说明了我们方法上的什么缺陷、以及需要补的能力。
> 写作目的：这些困难不是"算法太难"，而是**方法层面的结构性缺口**在反复收费。

---

## 1. "候选被过滤光"型死锁，换着花样反复出现

**现象**：机器人有锁、有未完成房间、地图也在，但规划器**一个可派发目标都产不出**，`cmd_vel` 恒为 0，直到看门狗终止。

**反复的证据（每一轮都是不同的过滤器）**

| 轮次 | 池子被谁清空 | 诊断字段 |
|---|---|---|
| run46 | 前沿 id 与"前沿站点"不一致 → 全被 `wrong_topology` 拒（129 次） | `candidate_reject_counts.wrong_topology` |
| run48 | 对面房门 along 漂移 → 穿越路径全失败（63 次） | `path_unreachable` |
| run50 | 房间内部从未观测 → 分段穿越"全有全无"失败 | `path_unreachable` + 门带 0 格 |
| run55 | 锁定房间**零候选生成**（房内全未知） | `tgt=None`、`cand=1` |
| run58 | 激光前沿被拓扑过滤、54 个相机候选被判 `unconfirmed_topology` | `last_reject_reason=CANDIDATE_TOPOLOGY_MISMATCH` |
| run61 | 候选在**路由阶段**才全部失败（兜底在路由之前） | `path_unreachable` |
| run64 | 全图**连候选都没生成**（"走廊探完、房间产不出视点"） | `generated_kind_counts={}` |

**方法缺陷**：目标生成是一条**过滤器链**，而我们**从未声明不变量**。任何过滤器组合都可以把池子清空，于是我们只能"失败一次、补一个兜底"（相机兜底 → 巡游 → 门口接近 → 释放锁 → 标记 BLOCKED）。兜底越多，状态空间越大，新的空集组合又会出现。

**需要补的能力**
- 一条**明确不变量**："只要本层还有未完成房间，规划器必须始终能给出至少一个已验证安全、可达、且不重复的动作"。
- 把兜底从"逐层补丁"收敛为**唯一的"安全动作生成器"**（按信息增益排序的候选族：房内视点 / 区内容器走廊点 / 门口观测点），而不是四个 if-else 串联。
- 单元测试直接针对**不变量**（构造各种"空池"输入，断言必然有动作），而不是针对每个过滤器。

## 2. 拓扑 / 门户身份不稳定，导致"同一个门有多个名字"

**现象**：同一个物理门在不同时刻被识别为 `ROOM_L_10 / L_15 / L_43 / L_47 / L_38 …`；完成记账、前沿归属、穿越搜索、对面房判定各自用不同方式去对身份。

**反复的证据**：run46（首对房完成记不上，`front_rooms_complete` 恒 False）、run48（锁定 `ROOM_L_47` 而真实门是 `L_43`）、run50/run55（对面房选到漂移 bin）、run62/run64（每层重新探测导致 id 变化）。我们为此加了**几何容差匹配**（`doorways_match` 2.5 m、前沿站点几何完成、宽域沿搜索、锁定家族）——**四处**不同的地方各实现了一遍。

**方法缺陷**：**身份是由几何瞬时量派生的字符串**（0.5 m 分箱 + 沿墙位置），而不是一个**持久对象**。于是每个消费者都必须自己重新做匹配；每新增一个消费者，就多一处"忘了做容差匹配"的缺陷。

**需要补的能力**
- 一个**唯一的门洞登记表（doorway registry）**：按几何分配**持久 id**（首次观测分配，之后同侧邻近观测归并到同一 id；id 不随分箱变化）。
- 所有消费者（完成判据、前沿归属、穿越、对面房、参考层提示）**只认持久 id**，禁止再各自做几何匹配。
- 用回放测试固定"同一门在多次地图更新中 id 不变"。

## 3. "同一份数据，不同环节用了不同视图" —— 反复出现的隐性不一致

**现象**：同一个概念在两个环节用了两种口径，导致行为自相矛盾。

**反复的证据**

| 概念 | 冲突 | 轮次 |
|---|---|---|
| 导航栅格 | 路由用**去斑**图，路径校验用**未去斑**图 → 一条合法路径被恒判"不安全" | run47（门口自旋，A/B 目标每 5.5 s 交替） |
| 楼层地图 | 换层后仍用**上一层**的图规划 → A* 失败 654 次、5 分钟挪 2 m | run52 |
| 姿态 | 安全判据用 **FAST-LIO metric 姿态**（急转单点跳到 0.45 rad），机体 IMU 只有 0.12 rad | run63（`ROBOT_ROLLED` 误杀） |
| 时间 | 任务用**仿真秒**，看门狗用**真实秒** → 正常等待被判停滞 | run44/57 |
| 状态发布 | 状态是**事件驱动**的，"没有输出"被当成"死机/停滞"（freeze 监视器还在打印陈旧载荷） | run44/48/57 |

**方法缺陷**：每个概念缺少**单一事实来源（single source of truth）**；每个消费者随手选一个视图。这类缺陷不会在编译期暴露，只在运行时以"行为矛盾"的形式出现，且**每次都要花一整轮去发现**。

**需要补的能力**
- 对"地图 / 姿态 / 时钟 / 状态"四个概念各定义**唯一访问器**，其它地方禁止自行构造视图；在启动时打印一次"本次运行使用的视图"。
- 关键视图加**一致性断言**（例如：路径校验必须使用与生成该路径相同的栅格实例）。
- 状态发布改为**带序号与时间戳的周期发布**（而非纯事件驱动），让"沉默"与"停滞"可区分。

## 4. 组件静默死亡，"没有输出"与"任务停滞"难以区分

**现象**：某个 rospy.Timer 回调抛异常 → **线程永久死亡**；表面上任务像"卡住不动"，日志也停了，但没有任何错误行。

**反复的证据**：run44（`_control` 线程因 `UnboundLocalError` 死亡，机器人此后 cmd 恒 0，误判为"规划停滞"）、run57（`_plan` 线程静默死亡，日志停在 sim 219）、run60（错误属性导致控制循环每周期抛错，靠我们后加的护栏才留下 4274 条 `CONTROL_FAULT` 而非静默死机）。

**方法缺陷**：**活性（liveness）不是一等契约**。组件没有心跳、没有"活着但没进展"的表达方式；监控只能从副作用（覆盖率、日志）**推断**健康，于是推断错误频繁发生。

**需要补的能力**
- 每个长生命周期组件（控制环、规划环、建图、电梯、危险检测）发布**心跳 + 迭代计数 + 最近一次成功时间**；缺心跳即判故障。
- 心跳与"无进展"分离：无进展由不变量/兜底处理，缺心跳由监督层处理。
- 指标进 `result.json`，让"这轮到底是死了还是慢"一眼可判。

## 5. 看门狗反复误杀健康运行

**现象**：监控层把**正常等待**判成"停滞/异常"，反而终止了本可成功的运行。

**反复的证据**：run44/57（真实秒阈值 420 s ≈ 仅 38 仿真秒，落在"锁层稳定窗口"内）；run52（换层看门狗用真实秒，5 分钟的正常爬行被判异常）；run63（倾倒判据用 metric 姿态的单点跳变）。

**方法缺陷**：看门狗是**按症状逐个手写**的，各自定义"什么算正常等待"与"用什么时钟"；它们**不理解任务状态机**，因此必然与任务的真实语义错位。更糟的是：误杀会掩盖真正的缺陷（run57 的真实死因是 §4 的线程死亡，却被"看门狗杀停"抢了叙事）。

**需要补的能力**
- 一个**共享的监督库**：内置任务状态机的"合法等待"定义 + **统一仿真时钟**；所有看门狗基于它派生。
- 判定与动作分离：先产出**判定与证据**（verdict JSON），**终止运行**必须是显式、可审计的少数规则。
- 每次误杀都要进回归测试（当前已有的 sim 时钟改造应固化为测试）。

## 6. "一次只暴露一个缺陷" + 单轮 2 小时 → 尾段长期未被验证

**现象**：1 层剩余房间、2 层探索、下降/开门/返回出生点**从未端到端跑过**；每次阻塞都先出现在 0 层，修好后重启，又用两小时换一个新缺陷。

**反复的证据**：run46/47/48/49/50/52/54/55/57/58/59/60/61/62/63/64 —— 绝大多数轮的失败点都在**0 层或换层**；唯一一次推进到"两层完成"的是 run49（旧代码线），此后**没有任何一轮**走到 2 层。

**方法缺陷**：迭代方式是"**全流程端到端**"，而不是**分层验证**。RTF≈0.1 使每轮 ≈2 小时，于是"每轮只暴露一个缺陷"的代价被放大 5–10 倍；尾段的缺陷被 0 层的缺陷长期遮蔽。

**需要补的能力**
- **尾段可离线验证**：用已完成楼层存档的地图 + 状态机桩（stub explorer）驱动电梯/下降链路；只要能验证"状态链与判据"，就不必每次都真跑 2 小时。
- **缩短反馈环**：把"0 层阻塞"与"尾段验证"解耦（例如允许从 1 层/2 层直接起跑，或对上层使用合成地图）。
- 明确每轮的**假设与预期观测**（预注册），避免"跑完才知道要看什么"。

## 7. 参数蔓延：同名不同义、跨节点误用

**现象**：同一含义的常量在不同节点里各有一份、名字相近但语义不同；误用后只在运行时以异常或怪异行为暴露。

**证据**：run60 在探索节点里误用电梯节点的 `stop_distance`（应为 `motion_stop_distance`），每周期抛异常、整轮报废；`target_tolerance` 同时充当"到达容差"与"停止距离"的角色；多处 `*_tolerance` 语义重叠（`heading_tolerance`、`target_replace_*`、`station_tolerance`、`direct_align_tolerance`）。

**方法缺陷**：没有**参数归属与命名规范**；常量在节点间被复制粘贴；缺"属性是否存在"的编译期/静态保障（我们已补 `check_undefined_attrs.py`，但这只堵住了最外层）。

**需要补的能力**
- 每节点一份**参数契约**（名字、单位、含义、合法范围）并在启动时打印/校验；
- 语义化命名（带单位与对象，如 `arrival_distance_m`、`front_stop_distance_m`），禁止跨节点复用同名常量；
- 把静态检查扩展到"未使用的导入/未定义的参数键/魔法数"。

## 8. 修复集中在下游：越"放宽判据/加大搜索"，越掩盖上游缺失

**现象**：遇到失败时，我们反复的选择是"**把搜索放宽一点**"（宽域沿搜索、几何容差、路由去抖、目标冷却、多级兜底）。这些让当前症状消失，但同类问题在别处再现。

**证据**：run48 → 宽域沿搜索；run50 → 门口接近；run55/58/61/64 → 兜底链逐级加长。每一次都有效，但**"全图零候选"仍在 run64 复现**（只是换了位置）。

**方法缺陷**：多数失败的上游真因是"**机器人还没有观测那个地方**"（门内未知、走廊未建图、房间只被激光见过）。放宽规划器的判据并不能替代观测；正确的结构性动作是**先去看（observation-first）**。我们把"去看"做成了兜底（巡游/门口接近），但它仍排在过滤器链的末端、且受"已访问"等约束限制（run64 就因此失效）。

**需要补的能力**
- 把"**观测优先**"提升为**一等策略**：当某处长期无法规划/无候选时，主动生成"去观测"动作（门口观测、走廊推进），并把它排在**策略层**而不是兜底层。
- 对"未观测区域"显式建模（已知未知集合），规划器直接对它出目标，而不是等过滤器空掉再兜。

## 9. 判据分散，缺单一状态机契约

**现象**：完成判据、锁的获取/释放、分区准入、锁层、电梯闸门各有一套标志与条件（`completed_topologies`、`topology_states`、`lock_release_counts`、`retired_topologies`、`active_zone`、`front_rooms_complete`、`reference_floor_ready`…）。每次修复都**新增一个分支或计数器**。

**证据**：run46（`front_rooms_complete` 记不上）、run55（锁死）、run62（参考层闸门把已探索完的 0 层锁死）、run64（锁释放后仍无候选）。

**方法缺陷**：没有**单一状态机**与**不变量检查**；条件分散在多个函数与主题回调里，交互空间随补丁增长而爆炸（"锁 × 分区 × 兜底 × BLOCKED × 参考层"），于是新死锁不断涌现。

**需要补的能力**
- 把"楼层/房间/门"的完整生命周期写成**显式状态机**（状态、迁移、守卫、不变量），所有模块只通过它读写；
- 用**模型化测试**枚举状态×事件，断言不可达状态与死锁不存在；
- 关键不变量放进运行时自检（例如："锁着房间 ⇒ 该房间未完成 ⇒ 必有一个可派发动作"）。

## 方法层面的总结（这三条是根源）

1. **我们在用"补丁叠加"对抗"耦合爆炸"**：每轮失败都补一个兜底/容差/看门狗，系统的状态空间随之增大，于是**下一轮的失效形态更多**。这解释了 §1、§8、§9 的反复。
2. **我们把"身份、视图、时钟、活性"这些横切关注点留在了各处自行处理**：于是同类缺陷在不同模块反复出现（§2、§3、§4、§5、§7）。
3. **我们的验证层级与迭代成本不匹配**：RTF≈0.1 的现实要求"离线优先、分层验证"，但主循环仍是"2 小时一次的全流程端到端"（§6），导致尾段（1/2 层与下降）长期不被覆盖，也放大了每一次错误的代价。

**因此，除了继续推进 run（见 `stage_b_current_work.md` §6），真正能改变"反复"的，是把上述横切关注点收敛为四个基础设施**：
**① 持久身份登记表　② 单一视图/时钟访问器　③ 组件心跳与显式监督　④ 显式状态机 + 不变量测试**。
