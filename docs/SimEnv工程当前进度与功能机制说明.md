## 1. 结论摘要

当前工程已经不只是“能进入三个小房间并检测红色障碍物”的状态，更准确的结论如下：

1. **SimEnv 基础仿真平台已经具备完整比赛环境能力**：可以随机生成多楼层室内楼栋、房间、走廊、楼梯、电梯、动态门、家具、危险源和干扰源，并启动 Unitree A1、Livox、RealSense、控制器、门/电梯服务和评估程序。
2. **单层无真值建图和基础导航链已经打通**：Livox 点云可转换为二维激光，Hector 可建图；系统发布独立的导航地图和探索地图，并已完成直行、原地转向和不可达目标的基础 `move_base` 验收。
3. **第一层小房间自主探索链已经形成闭环**：门洞不是从场景坐标表读取，而是根据在线激光和占据地图检测；机器人能够执行“沿走廊找门、回访门口、对准、进门、房内旋转扫描、退出、继续走廊探索”。
4. **四房完整成功已经出现，但跨随机种子稳定性仍未完成**：
   - 种子 `20260822` 的正式三层场景中，曾在 `252.202 s` 仿真时间内达到 `VISITED=4`、`floor_complete=true`、`danger_count=3`，正式监视器给出 `passed=true`。
   - 换到种子 `20260823` 后，多轮只能在规定窗口内完成 2 至 3 间；最近一轮还出现 Hector 崩溃。
   - 本文整理时，仍在运行的一轮现场状态已经变为 `VISITED=4、UNREACHABLE=1、FLOOR_COMPLETE=true`，说明它最终完成了四间房，但存在一个误候选，而且没有在原定监控窗口内形成正式通过记录。因此不能据此宣称已经跨种子稳定通过。
5. **红色球形危险源检测链已经实现并在正式场景中检测到多个目标**：当前使用 RGB-D 图像检测红色圆形目标，利用深度恢复三维坐标，再变换到 `world` 坐标并进行多帧确认和空间去重。它能够在核心测试中排除红色方块和绿色球体。
6. **现在的主要瓶颈不是“能否进一次房”，而是定位稳定性、稀疏激光语义、误门洞、四房跨种子复现和结果格式收尾**。
7. **多楼层自主探索尚未完成**：基础环境有三层、楼梯和电梯，但当前 `simnav` 行为是“单层四房探索”，还没有把楼层完成、电梯/楼梯切换、下一层重定位和全楼任务调度串起来。

## 3. 已有的 SimEnv 基础平台功能

### 3.1 随机场景生成

`auto.sh` 在每次启动时调用比赛场景生成器，默认参数为：

| 参数 | 默认值 |
| --- | --- |
| 楼层数 | 3 |
| 每层房间数 | 4 |
| 建筑占地 | 约 `20 m x 36 m` |
| 危险源数量 | `3:6` 随机范围 |
| 干扰源数量 | `4:8` 随机范围 |
| 机器人起点 | `(0.0, -3.2, 0.6)`，yaw `1.5708` |

生成内容包括：

- 各楼层地板、墙体、房间和主走廊；
- 楼梯、电梯井、电梯轿厢和各层电梯门；
- 主入口动态门；
- 房间家具；
- 红色球形危险源；
- 红色方块和绿色球体干扰源；
- Gazebo world/SDF、门配置、电梯配置、场景 manifest、公开队伍信息和裁判真值。

危险源和干扰源只放置在房间内部，并避开墙、家具、其他源以及房门保留区，避免目标本身堵住机器人进房路径。

### 3.2 危险源和干扰源定义

| 类型 | 颜色 | 形状 | 尺寸 | 是否计分 |
| --- | --- | --- | --- | --- |
| 危险源 | 红色 | 球体 | 半径 `0.15 m` | 是 |
| 干扰源 | 红色 | 方块 | `0.30 m` 立方体 | 否，误报会产生虚警 |
| 干扰源 | 绿色 | 球体 | 半径 `0.15 m` | 否，误报会产生虚警 |

因此当前口语中的“红色障碍物检测”，在比赛定义里应准确称为“红色球形危险源检测”。仅检测红色不够，还必须利用形状排除红色方块。

### 3.3 Unitree A1 和控制接口

基础平台使用 ROS1 Noetic、Gazebo Classic 和 Unitree A1：

- 状态 `2`：站立；
- 状态 `4`：RL 键盘行走；
- 状态 `6`：RL `/cmd_vel` 控制；
- 状态 `8`：摔倒后复位；
- `/cmd_vel` 为当前自主探索的统一运动指令接口。

当前工作区对控制链做了两项重要约束：

1. RL 状态使用机体 IMU 四元数和陀螺仪数据，不再依赖 Gazebo 基座真值姿态。
2. `IOROS` 已移除对 `/ground_truth/base_w`、`/ground_truth/base_trunk` 和四足真值位姿的订阅，避免正式算法通过控制器间接使用真值。

当前 RL policy 默认是 stair policy，也可以通过 `UNITREE_POLICY_PATH` 指定模型文件。自主导航不直接篡改策略动作或关节目标，只发送与官方控制方式一致的速度和转向指令。

### 3.4 传感器能力

当前主要传感器如下：

| 传感器 | 主要话题 | 频率/规格 | 当前用途 |
| --- | --- | --- | --- |
| 机体 IMU | `/trunk_imu` | 约 1000 Hz | 约束定位航向、提供姿态 |
| Livox Mid-360 | `/scan` | 约 10 Hz 原始点云 | 障碍、走廊、门洞和建图 |
| 点云转换 | `/livox/Pointcloud2` | 约 10 Hz | 通用点云输入和二维投影 |
| Livox IMU | `/livox/imu` | 约 1000 Hz | 可选惯性输入 |
| RealSense RGB | `/real_sense/rgb/image_raw` | 10 Hz，640x480 | 红球颜色和轮廓检测 |
| RealSense 深度 | `/real_sense/depth/image_raw` | 10 Hz，640x480 | 恢复危险源三维位置 |
| RealSense 点云 | `/real_sense/depth/points` | 10 Hz | 可选三维感知 |

传感器数据可以通过 `ENABLE_SENSOR_DATA`、`ENABLE_LIVOX`、`ENABLE_REALSENSE` 等环境变量独立开关。模型、link 和外观仍保留，关闭的是数据发布和插件负载。

当前 Livox 插件还做了启动稳定性和性能调整：

- 先将 ray sensor 设为 inactive；
- 等世界完成一次 update 后再激活，降低插件加载早期的初始化竞争；
- 关闭 Gazebo 射线可视化，减少 GUI/渲染负载；
- 使用降采样扫描模式；
- 显式链接 Gazebo 库，避免依赖旧系统中的固定 protobuf 库名。

### 3.5 动态门和电梯

平台提供：

- `/set_door_state`：打开/关闭主入口门或指定楼层电梯厅门；
- `/call_elevator`：将电梯轿厢移动到目标楼层；
- `door_config.yaml`：各门板开合位姿和动作时间；
- `elevator_config.yaml`：电梯服务楼层、当前楼层和轿厢位姿。

当前生成器已修正主入口门板完全打开后的横向偏移，避免门板仍侵占门洞；初始打开的门会直接生成在打开位姿。电梯门开口、轿厢朝向、门槛填充和楼层对齐也有生成检查。

这些能力已经存在于环境层，但当前自主算法还没有执行完整的“完成一层 -> 呼梯 -> 进电梯 -> 上楼 -> 出电梯 -> 重定位 -> 探索下一层”流程。

### 3.6 场景可视化调整

为了在 Gazebo 中观察多层建筑，二层、三层、屋顶和上层电梯门 visual 被设为约 `0.80` 透明。只修改 visual，不修改 collision：

- 上层仍然有真实碰撞；
- 机器人不会穿过透明楼板或透明墙；
- 该调整只服务调试观察，不改变物理场景。

### 3.7 公开信息、真值隔离和评估

算法允许运行时读取：

- 传感器和控制话题；
- `/set_door_state`、`/call_elevator`；
- `generated_building/team_scene_info.json` 中的公开起点、门/电梯 ID 和允许接口。

算法不应读取：

- `layout_metadata.json`；
- `building_config.json`；
- `competition_scene.world`；
- `scene_manifest.json`；
- `results/danger_truth.json`；
- Gazebo `model_states` 和 ground-truth 话题。

当前 `simnav` 门洞检测源码不读取房间坐标表、预设访问顺序、`layout_metadata` 或 `model_states`。`world` 对齐只使用公开 `team_scene_info.json` 中的 `robot_start`。

## 5. 建图、定位和地图机制

### 5.1 Livox 点云转二维激光

`pointcloud_to_laserscan` 将 `/livox/Pointcloud2` 投影到 `base` 坐标系：

- 高度范围：`0.08 m` 至 `1.50 m`；
- 水平角度：`-pi` 至 `+pi`；
- 角分辨率：约 `0.5 度`；
- 距离范围：`0.20 m` 至 `12.0 m`；
- 输出：`/scan_2d`；
- 实测频率：约 10 Hz。

高度过滤的目的是排除地面、腿部附近点和过高结构，将三维 Livox 数据压成适合二维走廊探索的 LaserScan。

### 5.2 Hector 建图

当前 Hector 关键参数：

| 参数 | 值 |
| --- | --- |
| 地图分辨率 | `0.05 m` |
| 地图大小 | `1024 x 1024` |
| 地图层数 | `map_multi_res_levels=2` |
| 扫描订阅队列 | `1` |
| 地图更新位移阈值 | `0.10 m` |
| 地图更新转角阈值 | `0.05 rad` |
| 地图发布周期 | `0.5 s` |

`map_multi_res_levels` 从默认 3 降为 2，扫描队列设为 1，是针对实时因子下降和旧扫描积压的稳定性修正。它降低了大范围匹配压力，但没有从根本上解决长走廊退化和偶发崩溃。

### 5.3 Hector 平移 + IMU 航向的混合定位

纯 Hector 在房间内旋转和侧向穿门时容易出现航向漂移。当前定位桥使用：

- `x/y`：来自 `/poseupdate` 的 Hector scan matching；
- `yaw`：首帧时对齐 Hector 航向和 `/trunk_imu`，之后使用 IMU 相对航向；
- `roll/pitch`：来自 IMU；
- `world` 初始对齐：使用公开的 `robot_start`；
- 输出：`/simnav/odom` 和 `/simnav/world_pose`。

TF 链为：

```text
world -> simnav_map -> simnav_odom -> base
```

这一设计解决了“房间旋转后 Hector yaw 明显错误”的问题，但平移仍依赖 Hector。因此长直走廊、稀疏结构、旋转后地图不一致仍会反映到机器人位置和危险源 `world` 坐标中。

### 5.4 Navigation Map 与 Exploration Map 分离

`map_views_node.py` 从 Hector `/map` 生成两张地图：

- `/navigation_map`：原始地图原样发布，供 move_base 和障碍规划使用；
- `/exploration_map`：在副本上执行小缝闭运算、入口 gate 和 defer zone 栅格化，供门洞识别和任务过滤使用。

该机制的核心原则是：**任务层过滤不能污染真实导航地图**。例如入口 gate 用来避免把主入口当作小房间门，但不会真的在导航地图中造一堵墙。

形态学闭运算只把小范围断裂补成占用，不会修改原始输入，也不会把远处未知区域无条件变成障碍。本文整理时，两项地图单元测试均通过。

## 6. 基础导航机制

`move_base` 使用：

- 全局规划器：Navfn；
- 局部规划器：DWA；
- 全局地图：`/navigation_map`；
- 局部障碍：`/scan_2d`；
- 里程计：`/simnav/odom`；
- 机器人 footprint：约 `0.68 m x 0.36 m`；
- 禁止横移：`max_vel_y=min_vel_y=0`；
- 最大前进速度：`0.60 m/s`；
- 最大规划角速度：`0.45 rad/s`。

禁止横移是因为 Unitree RL 策略在收到 DWA 的“前进 + 横移 + 转向”组合时，可能以低抬腿方式侧滑，实际运动与二维全向底盘假设不一致。

基础验收曾得到：

- 走廊直行目标 `(0, 3)`：`14.5 s` 仿真时间到达，最终位置误差 `0.155 m`；
- 原地转向 90 度：`3.4 s` 到达，航向误差 `0.134 rad`；
- 占用栅格不可达目标：`38.65 s` 后进入 `ABORTED`，没有无限等待；
- 实测最大线速度 `0.392 m/s`、最大角速度 `0.600 rad/s`。

需要注意：当前房门近距离动作不完全交给 DWA。实际测试发现，DWA 门前目标可能因定位漂移、非完整约束和贴墙代价而超时，所以门前对准、直线进门、扫描和退出由显式状态机直接发送 `/cmd_vel`。

## 7. 走廊探索和门洞检测机制

### 7.1 不使用房间坐标先验

当前运行时没有“小房间坐标列表”，也没有固定“先左一、再右一”的访问顺序。候选只能由：

- `/scan_2d` 的在线侧向开口时序；
- `/exploration_map` 的局部墙体几何；
- 当前 `/simnav/odom` 位姿；
- defer zone 等公开任务过滤信息

产生。

早期曾使用 `min_opening_progress=10.0` 过滤入口大厅，虽然它不是房间目标坐标，仍属于场景距离先验。该参数和分支已经删除。

### 7.2 走廊上下文确认

系统不会看到一个侧面开放就立即认为是房门。它先确认机器人处于细长走廊：

1. 从左右宽扇区取最近有限回波；
2. 左右墙距离都必须在合理范围；
3. 两侧墙间总宽必须持续落在 `1.7 m` 至 `2.7 m`；
4. 该双墙证据沿行进方向持续至少 `2.0 m`；
5. 地图链还会检查约 `5.0 m` 范围内两侧平行墙的支持率和偏差。

这套结构判据用于排除入口大厅、楼梯/电梯核心区、宽开放区和房间内部。

### 7.3 激光时序门洞检测

激光链使用左右正侧方窄扇区：

1. 只统计有限回波；Livox 的 `inf` 表示无回波/未知，不直接解释为 12 m 自由空间；
2. 窄扇区中位距离超过 `2.5 m` 时，记录开放区开始位置；
3. 等重新看到侧墙后再闭合测量，不在开放宽度刚到 `0.8 m` 时立刻出候选；
4. 完整开放宽度必须在 `0.8 m` 至 `1.6 m`；
5. 更宽的大厅和大门直接丢弃；
6. 根据当前走廊方向、墙距离和开口中心在线计算 `pre_pose`、`post_pose` 和门法向。

“必须等到闭合边出现”是防止大厅在宽度增长过程中短暂经过合法房门宽度、从而被误报为小门的关键修正。

### 7.4 地图几何门洞检测

地图链在机器人附近约 `4 m` 局部窗口内：

1. 提取占用栅格；
2. 投影到当前走廊方向和法向；
3. 找左右主墙面；
4. 在主墙面占用序列中寻找有两侧边界的空隙；
5. 空隙宽度需在 `0.8 m` 至 `1.6 m`；
6. 从门前到门后的 9 个采样点必须已经观测为自由栅格；
7. 候选不能落入 defer polygon；
8. 相近、同方向的墙面碎片会合并。

地图链能利用累积结构，激光链能在 Hector 把门口错误涂成实墙时继续发现真实开口。两条链互补，但也必须共享状态门控和空间去重，避免一间房生成多个候选。

### 7.5 候选生成门控和去重

门洞发现只允许在：

```text
active_candidate_id == None
并且 motion_state == CORRIDOR_PROGRESSION
```

也就是说，`GO_TO_PRE_DOOR`、进门、房内旋转和退出期间，激光链和地图链都不能新增房间候选。该修正用于防止房内旋转和漂移地图把家具、门内结构识别成新门。

候选还会按中心距离和门法向去重。正式参数中的空间去重半径为 `1.5 m`，用于吸收定位量化和两条检测链的坐标偏差。

### 7.6 走廊推进、避墙和有限回扫

当前走廊控制参数：

| 行为 | 参数 |
| --- | --- |
| 直行速度 | `0.60 m/s` |
| 分段进度 | `2.5 m` |
| 单窗口超时 | `15 s` 仿真时间 |
| 前方停车距离 | `0.50 m` |
| 转向速度 | `1.0 rad/s` |
| 航向对正上限 | `18 s` |
| 近墙阈值 | `0.75 m` |
| 最大反向扫掠 | 3 次 |
| 最大走廊转向 | 8 次 |

走廊控制同时使用：

- Hector 相对横向误差；
- 左右宽扇区净空差；
- 左右最近有限回波；
- 前方有限回波的 20 分位数。

只有左右都像墙时才使用净空差居中，避免单侧房门开放把机器人吸向门内。某侧出现小于 `0.75 m` 的最近回波时，启用更强的离墙航向修正。

到达端墙或持续无里程进展时，系统不会立即宣布楼层完成，而是：

1. 先判断左右开放方向在在线地图中是否真的是宽入口、细长走廊；
2. 小门宽瓶颈后的内部空间不能当作垂直走廊；
3. 没有合法分支且已访问房间不足 4 间时，后退离墙；
4. 原地转身 180 度；
5. 保留同一条走廊上下文并反向扫掠；
6. 最多执行 3 次，避免无限往返。

## 8. 进房、扫描和退出状态机

每个门洞候选的完整成功序列是：

```text
DISCOVERED
  -> GO_TO_PRE_DOOR
  -> ALIGN_TO_DOOR_NORMAL
  -> DOOR_CROSSING
  -> REACH_POST_DOOR
  -> ROOM_SCAN
  -> EXIT_ROOM
  -> VISITED
```

### 8.1 `GO_TO_PRE_DOOR`

- 候选按机器人到门前点的距离排序，优先处理最近候选；
- 如果门洞确认时机器人已经驶过门中心，不直接倒车；
- 系统先原地转身 180 度，再使用官方前进步态回访门中心；
- 沿走廊误差小于约 `0.45 m` 时认为到达；
- 速度 `0.45 m/s`，上限 `30 s`；
- 前方小于 `0.50 m` 时按阻挡失败处理。

由“倒车回访”改成“转身后前进”，是因为 A1 后向 Livox 净空常只有 `0.46-0.50 m`，旧方案会被安全阈值连续拒绝。

### 8.2 `ALIGN_TO_DOOR_NORMAL`

- 使用在线候选计算出的门法向，不使用房间坐标；
- 航向误差小于 `0.07 rad` 认为对准；
- 转向命令幅值 `1.0 rad/s`；
- 最长 `18 s` 仿真时间。

较小的 `0.4 rad/s` 命令在官方 RL 步态中曾出现“命令在发、IMU 实际角速度接近零”的情况，因此提高到和官方键盘 `J/L` 一致的量级。

### 8.3 `DOOR_CROSSING`

- 对准后直线穿门；
- 速度 `0.60 m/s`；
- 固定动作上限 `4.2 s`；
- 前方净空小于 `0.30 m` 时立即停止并判失败；
- 允许小幅角速度修正，但不依赖 Hector 计算精确穿门距离。

固定仿真时间加实时急停，是对 Hector 穿门期间平移漂移的折中：不相信其绝对位移，但仍用激光避免撞墙。

### 8.4 `REACH_POST_DOOR`

该状态是明确的状态机边界，表示穿门动作完成并准备进入房间扫描。当前节点中它会立即推进到 `ROOM_SCAN`，主要用于记录完整访问链和后续扩展。

### 8.5 `ROOM_SCAN`

- 原地旋转；
- 角速度 `1.0 rad/s`；
- 累计旋转接近 `2*pi` 后完成；
- 最长 `30 s`；
- 危险源检测频率从行走时的 5 Hz 提高到 15 Hz。

旋转使用当前混合定位航向累计角度。若定位不再更新，1 秒保护会优先停车，而不是继续盲转。

### 8.6 `EXIT_ROOM`

退出被拆成两个独立阶段：

1. `EXIT_ALIGNING`：转向门外方向，最多 `18 s`；
2. `EXIT_TRANSLATING`：直线驶出，最多 `3.0 s`。

退出阶段前方小于 `0.30 m` 时停止。早期尝试过“看到对侧墙就判定已到走廊”的传感器停止条件，但房内家具也可能产生相同距离，导致过早结束；该判据已经回退。

如果退出失败，只重试 `EXIT_ROOM`，不重新执行进门，避免机器人已经在房内却再次向房间深处穿越。

### 8.7 重试、不可达和完成条件

- 每个门候选最多尝试 4 次；
- 非退出阶段失败后可回到 `DISCOVERED`；
- 超过上限标为 `UNREACHABLE`；
- `UNREACHABLE` 不能代替 `VISITED`；
- 至少 4 个候选达到 `VISITED`；
- 所有已知候选进入终态；
- 连续 8 秒仿真时间没有新候选；
- 然后停车并发布 `/simnav/floor_complete=True` 和 `FLOOR_COMPLETE`。

### 8.8 定位失效保护

探索节点记录最后一条 `/simnav/odom` 的仿真时间。如果：

- 尚未收到首帧定位；或
- 定位超过 `1.0 s` 未更新，

则立即发布零速度并进入 `LOCALIZATION_STALE`。该保护已经在 Hector 停止发布和崩溃现场触发，能够避免机器人继续使用旧姿态盲走。

## 9. 红色球形危险源检测机制

### 9.1 RGB-D 同步

检测节点订阅：

- `/real_sense/rgb/image_raw`；
- `/real_sense/depth/image_raw`；
- `/real_sense/rgb/camera_info`；
- `/simnav/explorer_status`。

RGB 和深度使用近似时间同步：队列 8，允许时间差 `0.08 s`。正常行走时最多处理 5 Hz，`ROOM_SCAN` 时提高到 15 Hz。

### 9.2 红色分割

RGB 图像转 HSV 后合并两个红色色相区间：

```text
H: 0-10 或 170-179
S: 90-255
V: 60-255
```

随后进行 `3 x 3` 形态学开运算和闭运算：

- 开运算去掉小噪点；
- 闭运算补齐目标内部的小孔洞。

### 9.3 球形轮廓筛选

每个红色轮廓需要满足：

| 条件 | 当前阈值 |
| --- | --- |
| 最小面积 | `80 px` |
| 最小圆度 | `0.82` |
| 外接框宽高比 | `0.78-1.28` |
| 最大矩形填充率 | `0.88` |
| 外接圆半径 | `5-180 px` |

圆度使用：

```text
4 * pi * area / perimeter^2
```

红色方块通常矩形填充率高、圆度或轮廓特征不满足球形条件，因此被拒绝；绿色球体在颜色分割阶段就被拒绝。

### 9.4 深度和相机坐标恢复

系统在圆心附近、半径约 `0.35` 倍的中心窗口取深度：

- 只保留有限值；
- 深度范围 `0.15 m` 至 `12.0 m`；
- 至少需要 6 个有效像素；
- 使用中位数抵抗噪声和边缘背景。

然后根据相机内参恢复三维坐标：

```text
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
Z = median_depth
```

### 9.5 变换到 world 坐标

每个相机坐标点按图像时间戳查询 TF，并变换到 `world`。该变换依赖当前定位链，因此危险源坐标精度最终受 Hector 平移漂移影响。

### 9.6 多帧确认和空间去重

当前跟踪器参数：

- 空间聚类半径：`0.60 m`；
- 确认帧数：3；
- 同一聚类中的坐标使用累计均值更新；
- `confidence = min(1, observations / 3)`；
- 相距超过 `0.60 m` 的观测建立新轨迹。

只有至少 3 帧的轨迹进入确认输出，能够降低单帧颜色噪声和瞬时深度异常造成的误报。

### 9.7 输出

节点发布：

- `/simnav/danger_poses`；
- `/simnav/danger_markers`；
- `/simnav/danger_tracks`；
- `results/detected_danger.json`。

文件采用“先写 `.tmp`、再原子替换”的方式，避免程序被中断时留下半个 JSON。

当前内部输出示例字段为：

```json
{
  "frame_id": "world",
  "dangers": [
    {
      "id": 1,
      "position_world": [1.0, 2.0, 0.15],
      "observations": 5,
      "confidence": 1.0
    }
  ]
}
```

**重要未完成项**：官方评估脚本要求的是 `exploration_time` 和 `detected_danger_sources[].position`。当前检测节点写出的仍是内部跟踪格式，评估器不会直接接受。最终提交前必须增加格式适配或修改节点正式输出结构，同时保留调试轨迹信息到另一个文件/话题。

## 11. 当前碰到的主要难点和具体根因

### 11.1 长走廊中的二维激光定位退化

这是当前最核心的问题。

长直走廊的左右墙高度重复、沿走廊方向几何变化少，scan matching 对纵向平移约束弱。已经观察到：

- 实际机器人走了较远距离，Hector 只累计较小平移；
- 机器人已经接近后半段房门，算法却认为进度不足；
- 穿门和房内旋转后发生大幅平移漂移；
- 门洞坐标、回访方向和退出距离被错误位姿影响；
- 极端情况下最大单帧跳变超过 2 m；
- Hector 最终可能报 `SearchDir angle change too large` 并崩溃。

IMU 只能显著改善 yaw，不能直接修复 Hector 的 `x/y` 退化。

### 11.2 Livox 稀疏回波和 `inf` 的语义

Livox 不是均匀二维雷达。投影到 LaserScan 后，某个扇区常同时包含少量真实近点和大量 `inf`。

曾出现的错误包括：

- 把 `inf` 填成 12 m，再参与前方 20 分位，端墙被误判为 12 m 净空；
- 把 `inf` 参与侧向中位数，真实墙被误判为开放；
- 全部无有限回波时，无法区分“真正开口”和“当前扫描模式没有打到物体”。

当前修正是：

- 前方净空只统计有限回波；
- 侧面窄扇区只统计有限回波；
- 全无有限值时记为未知，不直接作为门洞开放/闭合证据；
- 走廊结构使用更宽扇区的最近有限回波。

但随机姿态和家具仍可能改变有效回波比例，这是跨种子波动的重要来源。

### 11.3 腿式机器人不是理想二维速度底盘

Unitree A1 的 RL 控制存在明显执行特性：

- 小角速度命令可能几乎不响应；
- 横移组合命令会导致低抬腿侧滑；
- 实际线速度和角速度不一定达到命令幅值；
- 门槛、入口台阶和贴墙时可能持续收到前进命令却不推进；
- 后退步态和后向净空不适合当前门口回访。

因此传统 move_base/DWA 的连续速度假设不能直接照搬，当前采用非完整约束和显式门动作状态机进行补偿。

### 11.4 门洞检测要同时避免漏检和误检

典型漏检原因：

- Hector 将门口更新为连续占用墙；
- Livox 正侧窄扇区没有有限回波；
- 门洞在机器人驶过后才完成跨帧闭合确认；
- 定位横向漂移超过地图检测走廊带。

典型误检原因：

- 入口大厅的侧向开放；
- 宽大厅在开放宽度增长过程中短暂经过 0.8-1.6 m；
- 房间内部细长区域被误作垂直走廊；
- 房内旋转时漂移地图形成假门；
- 同一门由激光链和地图链分别生成候选。

当前已经增加完整闭合宽度、细长走廊证据、入口瓶颈、状态门控和空间去重，但现场仍出现一个额外 `UNREACHABLE` 候选，说明该问题尚未完全收敛。

### 11.5 进房和退出不能完全依赖当前里程计

门内动作恰好是 Hector 最容易退化的阶段：侧向离开走廊、近墙、家具遮挡、原地旋转。早期使用位姿距离控制时，机器人实际已经进房，算法仍认为距离不够并继续深入。

当前改用固定仿真时间 + 激光急停，但它也有代价：

- 不同实时速度下实际位移不完全一致；
- 家具可能造成提前急停；
- 固定退出时间可能过短或过长；
- 无法精确判断机器人是否已经回到走廊中心。

这是一种当前可工作的工程折中，不是最终的高精度门穿越方案。

### 11.6 Gazebo 实时因子和控制器启动稳定性

三层场景、Livox 射线、RGB-D、A1 关节控制和 SLAM 同时运行时负载较高。已经遇到：

- Gazebo 实时因子低于 1；
- 传感器墙钟频率下降；
- ROS 队列积压旧扫描；
- 12 个关节控制器加载停在单个 `load_controller`；
- `/clock` 长时间为零；
- 在机器人/控制器未就绪时切状态导致测试无效。

当前使用无 GUI、传感器可选开关、Livox 降采样、扫描队列 1、先暂停启动再解暂停等方式降低风险，但完整启动流程仍需要等待关节反馈、状态 2 稳定至少约 1.5 秒，再切状态 6。

### 11.7 完成时间和跨种子复现

种子 `20260822` 能在约 252 秒通过，不代表随机种子都能在 360 秒完成。`20260823` 的现场轮次最终达到四房，但超过原监控窗口并产生一个误候选。

当前必须分别统计：

- 是否最终能完成；
- 是否在规定仿真时间内完成；
- 是否存在误候选/不可达；
- 是否检测到全部危险源；
- 是否发生定位跳变或节点崩溃。

不能只用最终 `VISITED=4` 代替稳定性验收。

### 11.8 危险源坐标依赖定位精度

红球像素和深度可以正确恢复到相机坐标，但最终评分使用 `world` 坐标。Hector 平移漂移会整体影响危险源坐标，并可能让同一红球的多帧位置相差超过 `0.60 m`，造成轨迹分裂或重复检测。

因此危险源检测的剩余问题不只是视觉阈值，还包括定位、TF 时间同步和空间聚类阈值。

### 11.9 正式结果文件格式尚未闭环

当前内部检测 JSON 与评估器要求不一致：

- 当前：`frame_id + dangers[].position_world`；
- 评估器：`exploration_time + detected_danger_sources[].position`。

如果直接运行正式评估，评估器会报告缺少 `exploration_time`，并读不到检测位置。这是提交前必须修复的接口问题。

### 11.10 多楼层任务尚未串联

虽然基础平台已经有楼梯、电梯和动态门，但当前探索状态只有单层完成。还缺少：

- 楼层 ID 和高度状态管理；
- 电梯/楼梯选择；
- 进出电梯的可靠控制；
- 电梯运动期间的感知暂停和安全状态；
- 新楼层局部地图初始化或多地图管理；
- world 坐标 z 更新；
- 跨楼层危险源汇总；
- 全楼任务完成判定。

### 11.11 工作区可复现性和工程卫生

当前新增 `src/simnav/`、`team_scripts/`、`run_navigation.sh` 和阶段文档仍是未跟踪文件，其他修改也尚未提交；同时仓库中存在大量 build/devel、`__pycache__`、日志和生成场景改动。

这会带来：

- 无法仅靠 Git commit 精确恢复当前成功版本；
- 容器内 `.simenv_build/devel` 可能和源码时间不同；
- 生成文件噪声掩盖真正源码改动；
- 更换机器或重新编译时难以确认使用了哪套参数。

在继续大规模实验前，应先整理忽略规则、拆分源码/配置提交，并记录每轮 seed、commit、参数和结果。

## 12. 当前不能宣称已经完成的内容

以下说法目前都不严谨：

- “自主探索已经稳定完成”——固定种子成功，但随机种子限时稳定性未完成；
- “四个房间每次都能进”——多轮只有 2 至 3 间；
- “没有误门洞”——当前现场仍有 `UNREACHABLE=1`；
- “危险源结果可以直接评分”——输出格式尚不兼容正式评估器；
- “定位已经解决”——Hector 仍会漂移、跳变甚至崩溃；
- “已经支持三层自主探索”——当前只完成单层行为闭环；
- “当前结果文件属于正在运行这轮”——该文件早于本轮启动，是旧结果；
- “所有内容都已提交可复现”——当前大量核心内容仍在未提交工作区。

## 13. 建议的下一步优先级

### P0：先保证定位和实验可复现

1. 保存当前工作区源码和参数为明确提交，排除 build/devel/log/generated 文件。
2. 每轮测试固定记录：commit、seed、启动参数、仿真时间窗口、状态序列、最大位姿跳变、危险源数和结果文件。
3. 对 Hector 崩溃增加单独日志归档和退出码监控。
4. 评估继续调 Hector 的收益，或切换到更适合 Livox + IMU 的成熟定位方案；新方案必须继续满足“不使用 Gazebo 真值”。
5. 在定位方案稳定前，不建议继续堆叠多楼层状态机，否则问题会被放大。

### P0：完成随机种子单层四房验收

1. 先跑当前 28 项核心/地图测试。
2. 至少选择 3 至 5 个新随机种子。
3. 每个种子在固定仿真时间内无人干预运行。
4. 通过条件建议统一为：`VISITED=4`、`UNREACHABLE=0`、`floor_complete=true`、Hector 不崩溃、最大位姿跳变受控。
5. 对超时但最终完成的轮次单独记为“最终可达，限时失败”，不能混入正式通过率。

### P0：修复正式结果格式

1. 将内部跟踪输出保留在调试话题或独立文件；
2. 正式 `results/detected_danger.json` 写成评估器要求的 schema；
3. 从 `/clock` 记录 `exploration_time`；
4. 在任务完成或中止时原子写出最终结果；
5. 用裁判真值只做运行结束后的离线评分，不进入算法运行时输入。

### P1：收敛门洞误检和漏检

1. 把本轮额外 `UNREACHABLE` 候选的发现时刻、左右激光、走廊宽度、地图截图片段保存下来；
2. 给每个候选记录来源（scan/map/both）、完整宽度、走廊证据长度和发现状态；
3. 对候选做可解释的拒绝原因统计，而不是只看最终数量；
4. 验证 `1.5 m` 去重半径是否会误合并相邻门，或仍不足以吸收漂移；
5. 对全无有限侧向回波保持 unknown，避免重新引入“无回波等于大开口”。

### P1：提高危险源坐标质量

1. 保存每条轨迹的坐标方差和时间跨度；
2. 增加相机深度与目标像素尺度一致性检查；
3. 房内扫描阶段检查 TF 延迟和定位跳变；
4. 对同一房间内的重复轨迹做更稳健的后处理；
5. 用多个 seed 检查红球、红方块、绿球、遮挡和家具背景下的召回/虚警。

### P2：开始多楼层集成

只有单层稳定后，再增加：

1. `FLOOR_COMPLETE -> TRANSITION_SELECT`；
2. 门/电梯服务调用；
3. 电梯进入、关门、运行、开门和退出状态；
4. 楼层 z 与局部地图切换；
5. 各层房间计数和危险源结果合并；
6. 全楼完成和最终评分输出。

## 14. 常用启动、观察和测试入口

### 14.1 启动基础环境

在 ROS Noetic 容器内、工程根目录执行：

```bash
GUI=false PAUSED=true SEED=20260823 ./auto.sh
```

等待模型、关节和传感器就绪后，在控制器中先进入状态 2，按 `/clock` 等待至少约 1.5 秒，再进入状态 6。

### 14.2 启动定位、建图和基础导航

```bash
./run_navigation.sh
```

该脚本启动 `simnav.launch`，包含 mapping 和 navigation，不包含 Gazebo、控制器、RViz 或房间行为。

### 14.3 启动房间探索和危险源检测

```bash
roslaunch simnav stage_b_behavior.launch
```

### 14.4 观察状态

```bash
rostopic echo /simnav/explorer_status
rostopic echo /simnav/floor_complete
rostopic echo /simnav/danger_tracks
rostopic hz /scan_2d
rostopic hz /simnav/odom
```

### 14.5 核心测试

```bash
PYTHONPATH=src/simnav/scripts:$PYTHONPATH \
python3 -m unittest discover -s src/simnav/test -p 'test_*_core.py' -v

PYTHONPATH=src/simnav/scripts:$PYTHONPATH \
python3 -m unittest src/simnav/test/test_map_views.py -v
```

完整离线联调入口：

```bash
./team_scripts/run_stage_b_offline_tests.sh
```

运行该脚本前应确认测试端口未占用，并避免与需要保留的现场 ROS 进程发生清理范围冲突。

## 16. 最终状态判断

截至本文整理时，SimEnv 已经具备完整的比赛仿真底座，当前新增算法也已经跨过了“只能手动移动或单点检测”的阶段：机器人能够在不读取房间坐标和 Gazebo 真值的前提下，在线识别走廊与小门、进入房间、旋转扫描、退出并继续探索；红色球形危险源也能通过 RGB-D 和多帧跟踪输出 `world` 坐标。

当前阶段最合适的定义是：

> **单层四房自主探索与危险源检测主闭环已打通，固定种子正式通过过，随机种子可达到三房并最终出现四房结果；但定位稳定性、误候选、限时复现、正式结果格式和多楼层调度尚未完成。**

下一阶段不应再以“是否偶尔能进入第四间房”作为唯一目标，而应把重点转向“多随机种子、固定时限、零人工干预、定位不崩溃、无额外候选、结果可直接评分”的稳定验收。
