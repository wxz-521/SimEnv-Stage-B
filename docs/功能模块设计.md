# SimEnv Stage-B 功能模块设计（活文档）

> **用途**：本文件是 Stage-B 的**唯一设计记录**，包含现有功能设计、模块契约、变更记录。
> **维护规则**：**每次大改（功能块增删、接口变更、机制删除）后必须更新本文件的「变更记录」与相关章节**，并写明：改了什么、删了什么、依据、验证方式。
> **设计判据**（用户确定）：容差 + 失败代价 + 几何可分辨性 → **房间不识别门，电梯识别**。
> **第一原则**：不堆小机制。出问题先问"哪一块的职责没做到"，不在块之间加守卫/预算/防抖。

### T2a 设计表（先对齐语义，再写码）

**A. 单一准入函数**（替代目前散落在 4 个分支里的过滤）

```
admit(candidate, ctx) -> (bool, reason)
  ctx = { zone_now, zone_split, gate_source, gate_world, robot_pose, room_status, visited }
判定顺序（任一不满足即拒绝，reason 就是第一条命中的名称）：
  1 LOBBY            (p-gate)·forward < -0.5                  → 大厅禁区（永不允许）
  2 KIND             kind ∈ {LASER_FRONTIER, CAMERA_FRONTIER, SPHERE_REVIEW}
  3 CORRIDOR_CAMERA  topology==CORRIDOR 且 kind==CAMERA_FRONTIER → 走廊=相机前沿禁区
  4 BEHIND           (p-robot)·forward < -0.5                 → 身后禁选
  5 ZONE             topology 属于 zone_now 的房间，或 CORRIDOR 且 in_active_zone
  6 ROOM_UNEXPLORED  若 topology 是房间：room_status(topology) != COVERED
诊断：`admission_reject_counts[reason] += 1`（逐条计数，替代现在只有一个 wrong_topology 派生数）
```

**B. 可测不变量**（每条对应一个断言）

| 不变量 | 断言位置 | 违反时的含义 |
|---|---|---|
| 大厅候选 = 0 | `admit` 的 LOBBY 计数 | 又出现"往大厅走" |
| 身后候选 = 0 | BEHIND 计数 | 又出现"往回走" |
| 走廊相机候选 = 0 | CORRIDOR_CAMERA 计数 | 违反"走廊为相机前沿禁区" |
| 未探索房间目标数 ≥ 1 | `plan()` 返回前扫一遍 targets | 又出现"房间没前沿、走廊空转" |
| 前区完成 → 必进 TRANSIT_TO_FAR | 状态迁移断言 | "没去远区" |
| 走廊作为目标 ≤ 2 次/层 | 节点计数 | 走廊占比失控 |

**C. TRANSIT_TO_FAR 状态机**（把"去远区"从排序副产品提升为状态）

```
FRONT_DONE           前站两房都 COVERED（front_stations_complete 已有）
      ↓ 进入（一次性，写进节点状态）
TRANSIT_TO_FAR       只接受 zone_now==B 的候选；走廊直行为唯一候选
                     目标 = point_from_gate(gate, zone_split_along + margin)
                     判定：|沿走廊投影 - 该目标| ≤ 1.0 m → 到达
      ↓
SCAN_AT_DOOR         原地转 ±90°（5 个采样，复用 choose_opening_heading）
                     扫描期间把新出现的房内前沿吸进池子
      ↓ 有房内目标 → 立即派发，回 EXPLORE
      ↓ 无房内目标 → 小幅前进 1.5 m 再扫（最多 2 次），仍无 → 才允许走廊继续
```

**下一轮待办（用户已确认"下一次考虑调整"，本轮不动代码）**：
**T1 · 路径起点不在机器人脚下**：规划输入三者同系（`pose`←/simnav/odom、`grid`←/exploration_map、`gate_source` 均为源图），所以不是坐标系问题，而是 **A\* 从"最近可通行格"起步**：机器人自身航迹/门框散斑/膨胀余量把它所在格判死 → 起点被吸附到旁边。后果实测可见：机器人先往路径起点挪（甚至快出门）再折回来。**修法（O(1)，不碰 A\*）**：(a) 把机器人真实位姿前插为路径首航点（Nav2 等栈的标准做法）；(b) 在**已有那一次**导航场计算**之前**对机器人脚下清一个 ~9×9 格小圈；**(c) 绝不新增第二次距离变换**（那才会 +15 ms）。**验证口径**：先加诊断 `path_start_offset` / `robot_cell_clearance`，再用已加的 `last_plan_ms` 做前后对照，涨了就回退。
**T2 · 前区/远区约束与走廊占比**：需明确"远区直行做成状态（TRANSIT_TO_FAR）"、"走廊只允许作为目标两种情形"、"未探索房间必须有目标（激光优先、相机兜底）"、"到房门为界后原地转扫 ±90°"；并配可测不变量（未探索房间目标数≥1、大厅/身后候选=0、前区完成必发生远区跃迁、走廊作为目标≤2次/层）。
**T3 · 一条异常观测留档**：截图见 `d=21.65m` 且目标为 `ROOM_R_51`（走廊方向约 25.5 m 的远区房），而机器人在前区——与 T2 同属区域约束问题，待 T1 修完后用 `path_start_offset`/`last_plan_ms` 复看。

**⑩ 相机兜底候选必须在机器人前方（已执行，用户报告"该直行去远区却往回走"）**：⑨ 之后仍有回退——P3「远区先固定前行」**只在走廊兜底内排序**，而"房间目标优先于走廊"这句会在房间视点出现时丢掉走廊目标，于是决定权落到房间视点，而它**可能是机器人身后**（已完成的前区房尚存零散未观测格）→ 机器人往回走。改为兜底候选还需满足"沿走廊方向投影在机器人前方（≥ −0.5 m）"。

**⑨ 相机兜底不得接受大厅视点（已执行，用户报告"没探索完就去大厅"）**：④ 的兜底用 `topology_id != "CORRIDOR"` 判断"房间所有"，但**大厅在走廊带之外**、其格子拓扑是 `ROOM_*_UNASSIGNED`，于是大厅视点被放进目标池，机器人被派去大厅、房间还没探完。改为同时要求候选在**闸门以内（走廊侧）**：`(p − gate)·forward ≥ −0.5`。已加断言"大厅永不接受前沿点"。

**⑧ 倒车出电梯（已执行，用户提出，独立脚本验证后落主线）**：`_drive_distance(..., reverse=True)` 用负 `vx` 倒出轿厢，并**删除骑乘后的 π 转身**（`elevator_heading += π` 不再执行），`EXIT_ELEVATOR` / `EXIT_GROUND_FLOOR` 改为倒车。依据（独立全循环脚本 cycle04，走廊出生 → 上二楼 → 出梯 → 折返 → 上三楼 → 出梯，**PASS**）：转 π 方案 `ALIGN_EXIT` 29~30 仿真秒、正着出梯在 6 cm 门槛上卡满 35 秒预算并超时失败；倒车方案**整段 ALIGN_EXIT 消失、出梯 8~9 秒全部成功**，折返 `ALIGN_DOOR` 也从 23 秒降到 0（出梯后仍朝门），**两段循环从"未完成"变成 73.3 仿真秒全部完成**，真值 z 0.307→5.530、轿厢 1.030→6.230。**关键物理结论**：那条 6 cm 门槛**下去时必须后退姿态**（后腿先下），正着前腿先探会卡住。

**⑦ 澄清"卡住/计算很久"的观感（量测，非机制改动）**：用户多次报告"停在后区/门口不动""换目标计算了好久"。按**仿真时间**实测：24.9 仿真秒内机器人实际位移 **4.10 m**（`cmd` 在 `vx=0.60` 直行与 `wz=−0.65` 原地转之间交替），并未停住。量测根因是时间尺度：**RTF = 0.111 ⇒ 1 仿真秒 ≈ 9 墙钟秒**（出房门那一段 20~25 仿真秒 = 墙钟 3~4 分钟）。规划器本身不慢：真实地图 600×800（80×60 m，48 万格）上 `clearance` 场 15 ms，**128 个相机候选 × 600 点路径 = 23 ms**（最坏 1200 点 = 49 ms）；探索器 CPU 占用 41% 单核（24 核、load≈8，非瓶颈）；吃 CPU 的是 rviz 146% + gzserver 127% + junior_ctrl 67%。为把该判断变成硬数字，状态里新增 **`last_plan_ms`**（规划周期实际耗时）与 **`target_switches`**（目标更换次数）。**教训**：诊断必须用仿真时间，墙钟读数会把 3 仿真秒的机动误判成 18 秒卡死。

**⑥ 目标点可在到达前更换（已执行，用户明确要求）**：用户指出"到之前可以换**目标点**，而不只是朝向"。core 新增纯函数 `target_switch_allowed()`，node 新增 `_switch_active_target()` 接在"继续沿用活动目标"分支之前。**边界必须卡死**（旧的按分数比较换目标已因"来回换一小时"被删）：① 当前目标已持有 `target_switch_dwell`（默认 8 仿真秒）→ 防乒乓；② 候选必须是**房间所有**（`CORRIDOR` 不接受），且持锁时必须是锁定的那个拓扑 → 不从锁下面换走；③ **Pareto**：候选路径不得比当前更长（含小幅松弛）→ 换目标永远不会让路程变长；④ 增益需达 `gain_ratio`（默认 1.25×）且按目标真正服务的指标比（相机视点比 `camera_gain`，其余比 `combined_gain`）→ 近似候选不互换位置。契约测试 7 项（`TargetSwitchTest`）。

**⑤ 修视点朝向退化（已执行，用户提问驱动）**：`_camera_look_at` 原本返回未观测区的**质心**（环带 0.6–2.5 m）。质心在未观测区大致对称时必然退化到视点自身（房间中央、走廊、以及**刚进楼层相机图还是空**的情形），`atan2(0,0)` 把朝向塌缩成 0 rad —— 一个**固定世界轴**；门洞法向是 ±y，正好差 90°，即用户看到的"每次进门目标点都横着/朝门外"。实测（与 run90 一层数字一致的场景）**61 个门口视点全部 look_at==视点、偏离进房方向 90°**。改为**按方位分 16 箱取未观测面积最大的方向**（"朝向信息增益最大的方向"的字面实现，只要还有未观测格就不退化），并列时用 `preferred_yaw`（由走廊侧向推出"房间内部"方向）打破；修复后同一场景 **61/61 偏离进房方向 0°、无退化**。另：`FrontierTarget` 是 frozen dataclass，节点新增 `_refresh_active_heading()`，在**去目标的路上每周期用最新地图刷新活动视点朝向**（位置不动，避免旧的按收益换目标抖动）——即"进门时最终目标视点的方向会越来越健康"（用户设计意图）。

## 二、模块划分与接口（当前设计）

| 块 | 职责 | 识别？ | 输入 → 输出 |
|---|---|---|---|
| **A 定位** | 可用位姿与不确定度 | — | 雷达/IMU/里程计 → 位姿 + 不确定度 |
| **B 房间区域** | 走廊 + 小房间区域的划分；**进出 = 区域成员判定**；每区域覆盖/状态 | ❌ | 占用图 → 区域表 |
| **C 电梯门户** | 电梯/大堂的识别、预选、接近、对准、进出轿厢、跨层 | ✅ | 楼层完成 + 位姿 → 跨层动作 + 新楼层几何 |
| **D 规划** | 按 B 的区域阶段决定"下一个目标 + 一条路径" | — | 区域表 + 图 + 位姿 → 路径 |
| **E 导航** | 沿路径驱动、不碰撞 | — | 路径 + 位姿 + 激光 → `/cmd_vel` |
| **F 感知** | 房间相机覆盖 + 红球检测 | — | 相机/雷达 → 增益、红球确认 |
| **G 交接** | supervisor 编排：探索完成 → C → 新楼层 | — | 事件转发，不持状态 |

### 契约要点

- **B**：门 = 房间区域与走廊区域的**边界段**（按需算，无身份/证据/配对/合并）；**走廊 = 相机前沿禁区**；进出房间是**状态**（位姿落在区域），不是事件。
- **C**：保留识别与"对准才走"（`direct_alignment_ready`/`_drive_direct`/`_align`）；**电梯几何（`gate_source`、各层 gate、隔离门、大堂门户）只由 C 计算与发布**，探索器只消费。
- **D**：选定当前房间区域后只服务它，直到覆盖达标或判定不可达；**不评分式替换目标**。
- **E**：航向只来自路径；单一限速权威；障碍/卡住 → 抛失败给 D。
- **边界**：房间里**不允许**任何朝向/对准特例；电梯里**必须有**。

## 七、B1 区域化设计细则（待实施，先定语义再写码）

**唯一判定函数**（放 core，纯函数、可离线单测）：

```
region_of_point(point, gate_source, corridor_half_width, portals) -> region_id
  1. 换算 (along, lateral) = 走廊系坐标
  2. |lateral| <= corridor_half_width + margin        -> "CORRIDOR"
  3. 否则取该侧（lateral 符号）的 portal，要求
     |along - portal.along| <= max(portal.width/2 + margin, 1.0)
                                                     -> 该房间 region_id
  4. 其余                                             -> "UNKNOWN"
```

**区域表**（由区域划分 + `topology_region_mask` 得出）：

```
rooms[region_id] = {cells, floor, laser_coverage, camera_coverage,
                    status: UNSEEN | ACTIVE | COVERED}
```

- `status`：无覆盖 → UNSEEN；正在作业（当前锁 / 机器人在内）→ ACTIVE；覆盖率达标 → COVERED。
- **完成/退休/前对侧 = 全部由 `status` 派生**（删 `completed_topologies` / `retired_topologies` / `completed_front_sides` / `front_station_topologies`）。
- **进门 = `region_of_point(pose) == 锁定的 region_id`**（幂等状态，取代 P0.1 的门平面判定）；**出房 = 回程路径走完且 `region_of_point(pose) == "CORRIDOR"`**。

**它取代的东西**：`topology_id_for_point`(core:1015，8 m 半径启发式) / `_mark_room_entered_locked`(node:1998) 的门平面判定 / 2 套状态 / 4 套完成集合。

**验证**：
- 离线：`region_of_point` 单测（走廊/左房/右房/门前窗口外/UNKNOWN）；区域 `status` 派生单测。
- 在线：同一 seed 对照 run79，检查区域覆盖达标时刻与 `status` 序列；日志中不应再出现"同一房间二次进门"。

## 九、完整性判定的真值与风险（记录）

**真值来源**（用于"完整探索"核对）：
- `generated_building/layout_metadata.json`：`floors[i].rooms` 每层 **4 间**（含 `door_pose` 与 `bounds`）；`target_points.rooms.floor_{0,1,2}_room_{0..3}` → **共 12 间**。
- `generated_building/building_config.json`：`num_floors` / `room_count` / `target_points`（同为 12 间）。
- `generated_building/team_scene_info.json`：电梯 `served_floors=[0,1,2]`（三层）；`door_ids` 只含 `main_entrance` + 三层电梯门，**不含房间门**。

**风险（已识别，待跑完核对）**：门 id 是 **0.5 m 分箱**且随 SLAM 漂移，现场一层的门户证据出现 `ROOM_L_1 / ROOM_L_15 / ROOM_R_0 / ROOM_R_15 / ROOM_R_43 / ROOM_R_47 / ROOM_R_49 / ROOM_R_54 / ROOM_R_56` 共 9 个 id，而真实房间只有 4 间 → 多出的 id 是**同一物理门的分箱副本**。当前楼层完成判据是"已完成拓扑数 ≥ 4"，理论上可能被"4 个副本"满足而漏掉真实房间。

**一层真实布局（`layout_metadata.json` floors[0].rooms，走廊沿 y 轴、两侧墙 x=±1.1）**：

| 房间 | bounds | 门位姿 (x, y) | 归属 |
|---|---|---|---|
| room0 | x∈[-9.5,-1.1] y∈[7.85,21.88] | (-1.1, 14.87) | 左·前站 |
| room1 | x∈[1.1,9.5] y∈[7.85,21.88] | (1.1, 14.87) | 右·前站 |
| room2 | x∈[-9.5,-1.1] y∈[21.88,35.91] | (-1.1, 28.89) | 左·后站 |
| room3 | x∈[1.1,9.5] y∈[21.88,35.91] | (1.1, 28.89) | 右·后站 |

→ 与现场对应：已退休的 `ROOM_L_15 / ROOM_R_15` 即**前站两间真房**；`ROOM_R_43/47/49/54/56` 全是**右后门（y=28.89）的分箱副本**（走廊 along≈21）。

**为什么这会咬人（具体机制）**：`topology_region_mask` 按"同侧相邻已确认门的中点"切 Voronoi 带 → 同一扇门的多个副本被切成**多条窄带，各自有独立的覆盖分母** → 它们可以很快分别"达标"，于是"已完成拓扑 ≥ 4"可能由「前站 2 真房 + 右后门 2 个副本」满足，而**左后房（y=28.89 左侧）从未进入** → 违背"完整探索"。

- **结构性解法**：区域化（每间房 = 一个 Voronoi 区域，覆盖与完成都按区域算），即 §七 的 B1 折叠账本——**这是它的直接动机**。
- **最小修法（备选，待当前 run 证据决定是否启用）**：在**完成计数**处按 `doorways_match`（同侧 + |Δalong| ≤ 2.5 m）对已确认门**去重**，使"4 间"对应 4 扇**物理门**而不是 4 个 id —— 这是删除重复而不是新增机制。
- **跑完后的核对方法**：用 `layout_metadata.json` 的 12 间真值 + 最终 `room_coverages` / `retired_topologies` 逐间比对，确认无房间被漏（`verify_timeline.log` 提供全过程）。
